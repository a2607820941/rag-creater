# 聊天模块后续优化建议

## 文档目的

这份文档聚焦聊天模块在完成本轮瘦身和问题修复之后，下一阶段值得继续推进的优化方向。

这里的“优化”不是指重做产品，而是围绕下面几个目标继续提升：

- 降低后续维护成本
- 减少状态边界问题
- 提高流式交互稳定性
- 提高问题排查效率
- 为后续新增聊天能力留出更清晰的扩展空间

## 当前阶段的基础已经具备

经过本轮整理，聊天模块已经有了几个比较重要的改善：

- 页面层不再像之前那样把所有逻辑堆在一个超长文件里
- `/api/chat` 已经变成薄路由
- 不同 `chatMode` 已经有统一编排入口
- 会话切换闪欢迎页的问题已经修复
- 输入框发送后不立即清空的问题已经修复
- UI 可见乱码已经清理

这意味着下一阶段不必再从“止血”开始，而是可以进入“稳态优化”。

## 优化方向一：进一步明确前端状态边界

### 当前观察

虽然前端已经拆出了 `use-chat-session-controller`、`use-chat-stream`、`use-chat-attachments`，但聊天页面仍然存在一些典型的会话级状态和消息级状态交错问题，例如：

- 某些状态依赖当前会话，但不一定总是和会话切换同步重置
- 某些 loading/error 状态既影响请求流程，也影响 UI 分支
- 页面级状态与组件消费方式之间还存在一定耦合

### 建议

1. 明确状态分层

- 会话级状态：
  - `conversationId`
  - `chatMode`
  - `agentId`
  - `isLoadingMessages`
- 输入级状态：
  - `input`
  - `attachments`
  - `menuOpen`
- 流式级状态：
  - `loading`
  - typing queue 状态
  - 当前流控制器
- 临时功能状态：
  - `pendingSkillDraft`
  - `skillPublishState`
  - `conversationMenu`

2. 为“切换会话”建立更明确的状态重置规则

建议整理一份内部约定，明确：

- 切换会话时哪些状态必须保留
- 哪些状态必须清空
- 哪些状态必须等历史消息加载成功后再更新

3. 收敛页面层直接控制的 UI 临时状态

目前页面级 controller 已经比之前清晰很多，但后续如果继续加功能，建议避免再把新的弹窗状态、工具菜单状态、试验性状态不断堆回 controller。

### 预期收益

- 更少的“串会话”问题
- 更少的渲染条件误判
- 后续新增功能时更不容易把页面重新养胖

## 优化方向二：统一聊天视图状态机

### 当前观察

聊天右侧区域实际上已经隐含了几个视图状态：

- 未选中会话
- 已选中会话，消息加载中
- 已选中会话，无历史消息
- 已选中会话，有历史消息
- 正在流式输出
- 流式失败

目前这些状态已经比之前清楚，但仍然主要是依赖多个布尔条件组合推导出来的。

### 建议

引入一个更明确的“视图状态枚举”或派生值，例如：

- `idle`
- `loading-conversation`
- `empty-conversation`
- `ready`
- `streaming`
- `failed`

不一定要引入完整状态机库，只需要把右侧主视图判断收敛成一个可读性更高的派生状态即可。

### 预期收益

- 降低欢迎页、空状态、loading、消息列表之间的判断复杂度
- 减少未来再次出现“状态条件稍微冲突就闪 UI”的风险

## 优化方向三：强化流式交互稳定性

### 当前观察

当前流式链路已经可用，但这类交互天然容易在下面几类场景里出问题：

- 中途 stop
- 会话切换时旧请求未完全退出
- 弱网或超时
- SSE 中途中断
- 本地 typing queue 与服务端 token 流完成时机不一致

### 建议

1. 统一流式请求生命周期日志

建议在前端内部为一次消息发送形成统一链路标识，例如：

- 本地 messageId
- conversationId
- mode
- startedAt
- stoppedAt
- failedReason

不一定展示给用户，但对调试很有帮助。

2. 区分“用户主动停止”和“异常失败”

现在 UI 上已经有 stop 行为，后续建议在状态和日志层也明确区分：

- user-stopped
- network-failed
- server-failed
- parse-failed

3. 为 SSE 解析失败留一个兜底策略

如果未来遇到 SSE 数据格式边界问题，可以考虑：

- 标记当前 assistant 消息为失败
- 保留已收到的内容
- 给出轻量错误提示

### 预期收益

- 流式中断场景更容易排查
- 用户看到的失败状态更自然
- 后续接更多模型或更多模式时不容易失控

## 优化方向四：加强聊天模式扩展能力

### 当前观察

虽然现在已经有 `chat-orchestrator`，但随着后续模式继续增加，仍然需要小心两个风险：

- orchestrator 自己再次变胖
- mode 之间的前后端契约逐渐分叉

### 建议

1. 为每种 mode 建立更一致的内部接口约定

例如统一约定每个 mode service 输出：

- `answer`
- `citations`
- `knowledgeFiles`
- `ragSummary`
- 可选 trace 信息

2. 减少 mode 分支中的隐式特例

例如：

- 哪些模式允许 attachment 进入 prompt
- 哪些模式允许 knowledge capture
- 哪些模式需要 usage 上报
- 哪些模式需要 citations

这些建议逐步沉淀成显式配置或明确函数，而不是散落在多处 `if` 分支里。

3. 为新 mode 预留最小接入清单

例如新增模式时，至少需要补齐：

- 前端模式选项
- orchestrator 分发
- service 实现
- SSE 输出约定
- 会话模型更新逻辑
- 回归验证用例

### 预期收益

- 后续新增聊天模式时更可控
- 降低“加一个模式改很多地方”的维护成本

## 优化方向五：补齐聊天模块的可观测性

### 当前观察

这轮很多问题能修，是因为已经明确看到了现象。但如果以后遇到一些偶发问题，比如：

- 某个模式偶发失败
- 某个会话切换偶发错乱
- 某些消息只在弱网下异常

单靠用户口述会比较难定位。

### 建议

1. 在服务端增加更稳定的结构化日志

建议至少记录：

- conversationId
- chatMode
- agentId
- attachmentIds
- request start/end
- success/failure
- 错误类别

2. 在前端保留轻量调试信息

只在开发环境可见即可，例如：

- 当前 conversationId
- isLoadingMessages
- loading
- 当前 chatMode
- 当前消息数

3. 为关键失败点补充错误标签

例如明确区分：

- validation error
- conversation load error
- stream error
- publish error
- mode dispatch error

### 预期收益

- 出问题时更容易第一时间判断是前端状态问题、SSE 问题还是后端模式问题
- 降低后续线上排查成本

## 优化方向六：补齐针对聊天模块的回归验证清单

### 当前观察

本轮已经做了不少手工验证和构建验证，但聊天模块本质上是一个交互链路很长的功能，后续每次改动都很容易影响边界行为。

### 建议

建议为聊天模块固定一份回归 checklist，至少覆盖：

1. 会话相关

- 首次进入聊天页
- 新建会话
- 切换历史会话
- 删除当前会话
- 删除非当前会话

2. 消息发送相关

- 纯文本发送
- 纯附件发送
- 文本加附件发送
- Enter 发送
- 空内容拦截

3. 流式交互相关

- 正常流式输出
- 手动停止
- 中途报错
- 弱网切换会话
- 流式结束后消息落盘

4. 模式相关

- `knowledge-agent`
- `openai`
- `rag-openai`
- `agent`
- `skill-agent`

5. Skill 相关

- 生成草稿
- 保存草稿
- 发布成功
- 发布失败

### 进一步建议

如果后续条件允许，可以逐步把其中最关键的几条做成自动化验证，优先覆盖：

- 切换会话不闪欢迎页
- 发送后输入框立即清空
- 流式消息能正常出现

### 预期收益

- 降低改一处坏一处的概率
- 后续继续迭代时更有信心

## 优化优先级建议

如果要按投入产出比排序，建议优先级如下：

1. 前端状态边界收敛

原因：
这类问题最容易直接影响用户体验，而且已经证明聊天模块之前确实存在这类问题。

2. 聊天视图状态统一

原因：
可以继续减少 UI 闪烁、空状态误判、会话边界错乱。

3. 流式交互稳定性和可观测性

原因：
这是聊天模块最关键、也最容易在复杂场景里出问题的部分。

4. mode 扩展能力和统一契约

原因：
适合在后续新增功能前继续整理，避免模式越来越多后重新变复杂。

5. 自动化回归补强

原因：
收益长期稳定，但可以放在关键链路结构更稳之后推进。

## 总结

聊天模块目前已经从“超长页面 + 超长路由 + 多状态混杂”的阶段，进入到了一个相对可继续演进的状态。但这还不是终点。

下一阶段最值得做的，不是再追求一次大重构，而是围绕几个真正会持续影响维护和体验的点稳步推进：

- 继续收敛状态边界
- 继续简化视图状态判断
- 增强流式交互稳定性
- 增强日志与排查能力
- 建立更稳定的回归验证机制

如果这些点继续做下去，聊天模块后面无论是接更多 Agent、更多 Skill、更多模式，还是继续打磨体验，都会轻松很多。
