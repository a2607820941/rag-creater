# 聊天模块问题复盘

## 背景

这段时间针对聊天模块做了一轮较集中的整理和修复。最初暴露出来的是几个具体问题，例如页面闪回欢迎页、输入框发送后不立即清空、局部 UI 中文乱码，但继续往里看后可以发现，这些问题背后有一个共同特点：聊天模块原本承担的职责过多，页面、状态、请求、流式处理、模式分发和 Skill 流程耦合在一起，导致后续维护成本偏高，也更容易出现边界状态问题。

这一轮工作的目标不是重做产品功能，而是在不破坏现有对外接口和用户可见行为的前提下，对聊天模块做内部整理，并修复已经暴露出来的体验问题。

## 问题一：聊天页面和聊天路由过重

### 问题现象

- 聊天页主文件过长，页面同时承担布局、状态管理、消息流控制、附件上传、会话切换、Skill 相关弹窗等职责
- `/api/chat` 路由内部同时处理请求校验、会话创建、Prompt 组装、RAG 上下文准备、模式分发、Skill 流程、usage 上报等逻辑
- 后续修一个交互问题时，往往需要跨很多代码段一起看，理解成本较高

### 根本原因

页面层和路由层承接了过多业务逻辑，缺少清晰的职责边界。前端没有把页面控制、消息流、附件管理拆开，后端没有把模式分发和具体服务拆开，导致“一个入口文件包办一切”。

### 解决方式

前端做了页面瘦身：

- 将聊天页改成薄页面入口，只负责挂载聊天 feature
- 把主界面下沉到 `AgentChatFeature`
- 把页面级逻辑拆成多个 hook：
  - `use-chat-session-controller`
  - `use-chat-stream`
  - `use-chat-attachments`

后端做了聊天路由瘦身：

- 将 `/api/chat` 调整为薄路由
- 新增 `chat-orchestrator`，统一根据 `chatMode` 分发到：
  - `openai`
  - `knowledge-agent`
  - `agent`
  - `skill-agent`
  - `rag-openai`
- 将 Prompt 组装、附件上下文处理、direct chat 逻辑、skill-agent 逻辑分别下沉到独立 service

### 结果

聊天模块的整体结构变得更清楚了。后续再修会话切换、输入框、Skill 相关问题时，不再需要在一个超长页面文件里来回找逻辑，前后端职责边界也更明确。

## 问题二：切换历史会话时右侧闪回欢迎页

### 问题现象

点击左侧历史会话时，右侧聊天区域会短暂显示初始欢迎页：

- `Ask Embark anything`
- 默认输入框
- 空白初始状态

然后才显示目标会话的历史消息。

### 根本原因

切换会话时，历史消息加载前先把 `messages` 清空了，而右侧欢迎页的渲染判断又过于依赖“当前没有消息”。于是会出现这样一段中间状态：

- 当前会话其实已经切换了
- 但历史消息还没加载回来
- `messages.length === 0`
- UI 被误判成“未开始的新会话”

### 解决方式

- 增加 `isLoadingMessages` 状态，用来区分“会话已选中但历史消息正在加载”
- 切换会话时不再先清空旧消息
- 历史消息请求成功后再统一替换消息列表
- 欢迎页渲染条件改成：
  - 只有“没有选中任何会话，并且没有消息”时才显示欢迎页
- 对右侧状态做了明确区分：
  - 未选中会话
  - 已选中会话且消息加载中
  - 已选中会话但暂无消息
  - 已选中会话且有历史消息

### 结果

切换历史会话时，不会再闪回初始欢迎页。加载过程中可以保留旧内容或显示 loading 状态，历史消息加载完成后再切换到正确内容。

## 问题三：聊天界面出现中文乱码

### 问题现象

聊天主界面中有少量按钮和文案出现乱码，例如：

- `Skill 绠＄悊`
- `鍥炲埌搴曢儴`

### 根本原因

这是典型的文本编码或内容写入过程异常导致的可见 UI 文案损坏。问题不在逻辑层，而在具体展示文案本身。

### 解决方式

定位到聊天主界面文件中的可见文案，将乱码字符串替换为正确中文，例如：

- `Skill 管理`
- `回到底部`

随后对聊天相关目录做了检索，确认没有同类乱码残留。

### 结果

聊天界面可见文案恢复正常，没有继续影响交互和阅读体验。

## 问题四：发送消息后输入框不会立即清空

### 问题现象

用户输入消息并点击发送后：

- 用户消息已经正常发送
- AI 已经开始流式输出
- 但输入框中的内容不会立刻消失
- 必须等流式输出结束后，输入框才清空

### 根本原因

输入框清空时机放错了位置。发送逻辑里先执行了：

- `await sendMessage(nextInput)`

等整个流式请求和输出过程结束之后，才执行：

- `setInput("")`

由于 `sendMessage` 本身要等待 SSE 流式处理完成，所以输入框内容被一起拖到了最后才清空。

### 解决方式

调整发送流程：

1. 先读取当前输入内容
2. 保存为本次发送使用的文本
3. 立即清空输入框
4. 再调用原有 `sendMessage` 逻辑
5. 流式请求继续使用提前保存的文本，而不是依赖后续的 `input` 状态

同时保留了原有行为：

- 用户消息仍然会立即追加到消息列表
- AI 回复仍然继续正常流式输出
- 请求失败时只提示错误，不会把已发送内容重新塞回输入框

### 结果

点击发送和按 Enter 发送时，输入框都会立即清空，交互体验更符合聊天产品的直觉。

## 问题五：会话切换时局部状态可能残留

### 问题现象

在修复聊天主链路的过程中，还发现两个容易被忽略的边界问题：

- Skill 发布草稿状态可能在切换会话后残留到下一个会话
- 历史消息加载失败时，右侧可能继续显示上一个会话的旧消息

### 根本原因

这两个问题本质上都是“会话级状态没有随着会话切换一起归位”：

- 某些状态属于当前会话上下文，却没有在切换/新建/删除会话时同步重置
- 某些失败场景没有处理“旧数据继续停留在界面上”的后果

### 解决方式

- 在切换、新建、删除会话时，显式重置 Skill 发布相关状态
- 在历史消息加载失败时，清空当前消息显示，避免旧会话内容误留在右侧

### 结果

聊天模块的状态边界更干净，不容易出现“已经切到新会话，但界面上还是上一个会话的局部状态”的情况。

## 额外检查结论

在上述问题修复之外，还对聊天模块做了一轮针对性检查：

- 聊天相关 ESLint 检查通过
- `npm run build` 通过
- 全仓库 `npm run lint` 仍有失败项，但问题主要集中在文档、提炼等其他模块，不属于聊天模块本轮改动引入的问题

这说明聊天模块这一轮整理后，至少在类型、构建和主要代码路径上没有明显的大问题。

## 总结

这一轮聊天模块的问题，表面上看是几个分散的小 bug：

- 会话切换闪欢迎页
- 输入框发送后不立即清空
- UI 中文乱码
- 局部状态残留

但从根上看，核心原因是聊天模块过去承担了过多职责，状态边界也不够清晰。页面过重、路由过重、会话状态和消息状态耦合过深，才会让这些问题更容易出现。

这轮处理的价值，不只是把几个症状修掉，更重要的是把聊天模块的前后端结构梳理得更清楚了一些。后续继续迭代聊天能力时，页面、状态、模式分发、Skill 流程和流式消息链路都会更容易维护和排查。
